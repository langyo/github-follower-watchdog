GitHub Follower Watchdog — монитор подписчиков без сервера, целиком живущий внутри репозитория. Работает в три движения:

1. **Ежечасная проверка** — крон GitHub Actions запускает скрипт на чистом стандартном Python (без `pip install`, без этапов подготовки), который постранично читает публичный API подписчиков и завершается за секунды.

2. **Дельты записываются в git** — каждый прогон сравнивает свежий список с `data/current.json` и дописывает события подписки и отписки в журнал только на добавление `data/history.jsonl`. Коммит (`🔄 Sync follower snapshot.`) порождают только реальные изменения; спокойный час не пишет ничего вовсе — история git и есть журнал изменений.

3. **Дашборд на Pages** — каждое изменение передеплоит одностраничный дашборд (Vue 3 · TSX · SCSS · vue-i18n, 8 языков, тёмная и светлая темы), показывающий динамику числа подписчиков, хронологию подписок/отписок и текущий список.

Поверх сырого списка watchdog **собирает профиль каждого подписчика в строгих пределах rate-limit** (объём вкладов за год, баланс подписок/подписчиков, открытые репозитории, заполненность профиля, возраст аккаунта), а дашборд превращает эти факты в прозрачный балл 0–100, отделяющий вероятных живых людей от подозрительных ботов массовой подписки.

Сделайте форк — и он становится **вашим**: наблюдаемый аккаунт определяется владельцем репозитория, унаследованные записи сбрасываются при первом прогоне форка, а тот же workflow автоматически включает и разворачивает GitHub Pages для форка.

## Быстрый старт

Всё ниже занимает около двух минут после форка.

1. **Сделайте форк репозитория** — имя свободное; далее предполагается, что вы оставили `github-follower-watchdog`.

2. **Включите Actions в своём форке** — откройте в браузере `https://github.com/<вы>/github-follower-watchdog/actions`. GitHub по умолчанию отключает workflows в свежих форках; нажмите **I understand my workflows, go ahead and enable them**.

3. **Запустите первую проверку** — на той же странице Actions выберите в боковой панели **Watch** → **Run workflow** → **Run workflow**. (Можно поднять *Max accounts to enrich*, если хотите, чтобы баллы заполнились быстрее.) Первый прогон зафиксирует текущих подписчиков как базовую линию и опубликует ваш сайт.

4. **Откройте свой дашборд** — `https://<вы>.github.io/github-follower-watchdog/`. Дальше он обновляется сам каждый час — когда что-то изменилось.

Если первый прогон остановится на шаге *Configure Pages* — GitHub иногда не даёт токену workflow создать сайт — откройте `https://github.com/<вы>/github-follower-watchdog/settings/pages`, поставьте **Source → GitHub Actions** и запустите **Watch** ещё раз.

**Заполнить баллы быстрее (необязательно, но рекомендуется).** У токена Actions лимиты жёстче, чем у вашего собственного, а CI обогащает максимум `WATCH_ENRICH_CAP` (по умолчанию 40) аккаунтов за часовой прогон. При небольшом списке это мягкий разогрев — при тысяче подписчиков это ~25 часов прогонов CI, перемалывающих сброшенные запросы обратной засыпки, прежде чем каждая карточка получит балл. Сделайте первый проход на своей машине ещё до включения чего-либо:

```bash
git clone https://github.com/<вы>/github-follower-watchdog
cd github-follower-watchdog && npm --prefix site install
export GITHUB_TOKEN=$(gh auth token)   # свой токен: 5000 запросов/час
WATCH_ENRICH_CAP=200 just watch        # повторяйте, пока не увидите «no changes»
```

Затем закоммитьте полученные записи `data/` в ветку, откройте PR и влейте его — следующий часовой прогон возьмёт файл в работу и будет обновлять только устаревшее.

**Настроить частоту (экономия квоты CI).** Крон срабатывает каждый час, но все ручки, решающие, сколько реально работать, — обычные переменные репозитория — задаются один раз в **Settings → Secrets and variables → Actions → Variables** (`vars.*`), без правки workflow:

| Переменная | По умолчанию | Смысл |
| --- | --- | --- |
| `WATCH_INTERVAL_HOURS` | `1` | Минимальные часы между плановыми проверками. При `6` промежуточные часы завершаются за секунды, не трогая API — ни записей, ни сборки, ни деплоя. Ручные запуски **Run workflow** всегда проверяют сразу. |
| `WATCH_ENRICH_CAP` | `40` | Аккаунтов с профилями за прогон (макс. 200; поле Run workflow приоритетнее). |
| `WATCH_ENRICH_STALE_DAYS` | `30` | Через сколько дней обновлять факты подписчика. |
| `WATCH_USER` | владелец форка | Следить за любым другим публичным аккаунтом. |

Например, `WATCH_INTERVAL_HOURS=6` срезает около 83 % планового API-трафика, при этом динамика, хронология и баллы обновляются четыре раза в день.

**Где живут данные.** `data/current.json` — актуальный список, `data/history.jsonl` — журнал подписок/отписок только на добавление, `data/accounts.json` — факты по каждому аккаунту, из которых считается балл. Всё trio пишет только CI и коммитит в ваш форк — `git log -- data/` и есть полная аудитная линия: никаких внешних сервисов, никаких баз, доверять нужно только git.

**Наблюдать за кем-то ещё.** Задайте `WATCH_USER` в `.github/workflows/watch.yml` (или передайте аккаунт аргументом `just watch <login>` локально), чтобы следить за любым публичным аккаунтом вместо своего.

## Как это устроено

- `scripts/watchdog.py` — весь сборщик: ограниченная пагинация, атомарные записи, порядок «сначала снимок, потом журнал» (оборванный прогон может потерять одну строку хронологии, но никогда не задублирует события) и железное правило «при любой ошибке API ничего не писать» для снимка. Вторая фаза — обогащение по остаточному принципу: до `WATCH_ENRICH_CAP` (по умолчанию 40, максимум 200) аккаунтов за прогон через REST-эндпоинт пользователя плюс один пакетный GraphQL-запрос, запись только если факт реально изменился. При сбоях API фаза сама останавливается, а оставшиеся аккаунты подхватываются следующим прогоном; свежий форк сначала фиксирует список, а к оценке приступает со следующего прогона.
- `data/current.json` + `data/history.jsonl` + `data/accounts.json` — сами записи; **пишет только CI** (AGENTS.md §5).
- `.github/workflows/watch.yml` — ежечасный крон + ручной запуск + push: watchdog → коммит при изменении → сборка сайта → деплой на Pages. Часы без изменений пропускают сборку и завершаются за ~20 с; ветка с изменениями укладывается примерно в минуту. (GitHub отключает запланированные workflows после 60 дней неактивности репозитория — а коммиты с данными сами по себе активность.)
- `site/` — дашборд. Vite + Vue 3 на TSX (без `.vue` SFC) + SCSS + vue-i18n, 8 языков. Записи копируются в бандл как публичные ресурсы без изменений и загружаются в рантайме, поэтому изменение только данных никогда не требует пересборки приложения; подсчёт балла целиком идёт в браузере (`site/src/data/scoring.ts`).

## Модель балла

Балл намеренно объясним — очки складываются за классические человеческие сигналы, а два штрафных множителя понижают классические формы ботов:

| Сигнал | Очки |
| --- | --- |
| Баланс подписок/подписчиков (0 подписок, или соотношение ≤ 2) | до +25 |
| Вклады за последний год (GraphQL) | до +30 |
| Открытые репозитории | до +15 |
| Заполненность профиля (имя, био, компания, локация, блог) | до +10 |
| Возраст аккаунта | до +15 |
| Форма «массовой подписки» (подписок ≥ 500, подписчиков < 50) | × 0.5 |
| Форма «пустого аккаунта» (нет вкладов и нет репозиториев) | × 0.6 |

Группы **Люди** (≥ 60), **Сомнительные** (30–59) и **Похожи на ботов** (< 30) фильтруются на дашборде. Профили освежаются постепенно (случайная выборка, ~40 аккаунтов в час) и никогда не упираются в rate limit.

## Локальная разработка

```bash
npm --prefix site install   # один раз
just watch                  # один прогон watchdog (цель: владелец origin, или передайте логин)
just dev                    # dev-сервер сайта на :5174
just build                  # проверка типов + production-сборка
just lint-msg               # темы коммитов в master..HEAD (AGENTS.md §1)
```

`GITHUB_TOKEN` для простого снятия списка подписчиков необязателен, но обогащение аккаунтов (то есть баллы) работает только при наличии токена в окружении — `export GITHUB_TOKEN=$(gh auth token)`.
